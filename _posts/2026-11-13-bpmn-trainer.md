# Model, Replay, Simulate: A BPMN Trainer for the Seminar Room


- Media: 21 screenshots and 3 videos generated by Playwright, listed in [media/readme.md](./media/readme.md)

> The application UI and the video captions are German. All screenshots and videos come from automated end-to-end runs (`npm run media`), so they show the application exactly as tested.

---

## Why another BPMN tool?

Students learn BPMN notation quickly. Understanding **how a process behaves** takes longer: what an exclusive gateway really decides, why a parallel join waits, and what happens when one hundred applications arrive and only one person can check them.

bpmnsim combines a BPMN editor, a token replay and a resource-constrained calculation simulation in one browser application. This post walks through a typical seminar sequence, from the first diagram to a scenario comparison.

---

## 1. Modelling: the editor

The editor is based on bpmn-js. **New** loads a starter diagram; the context pad appends tasks, gateways and events directly at the selected element.

![Editor with starter diagram](./media/screenshots/01-editor-starter.png)
*The editor with the starter diagram: start event, task, end event.*

![Context pad of a task](./media/screenshots/02-editor-context-pad.png)
*The context pad of a selected task: append elements, connect, change the type, or delete.*

### Video: modelling best practice

<video src="./media/videos/editing-best-practice.webm" controls width="100%" poster="./media/screenshots/02-editor-context-pad.png"></video>

▶ [editing-best-practice.webm](./media/videos/editing-best-practice.webm) (about 1:45, German captions)

The video builds a small order process step by step and shows nine practices:

1. Name the start event as a state: "Bestellung eingegangen".
2. Name tasks as object + verb: "Bestellung prüfen".
3. Phrase the gateway as a question: "Ware verfügbar?".
4. Label every outgoing branch (ja / nein).
5. End every path in a named end state.
6. Enlarge tasks so long names stay readable.
7. Make responsibilities visible with a pool and lanes. In the simulation, lanes become resources.
8. Check the model by playing every path with the replay.
9. Save the model as a `.bpmn` file.

## 3. Understanding the process logic: token simulation

### Replay: step by step, with your own decisions

In **Replay** mode a red token walks through the process. **▶ Play** runs it automatically, and **⏭ Step** advances it one hop at a time.

![Replay token](./media/screenshots/09-replay-token.png)
*The red token after the first step.*

At an exclusive gateway the replay stops. Numbered buttons mark the possible paths, and the student decides.

![XOR branch choice](./media/screenshots/10-replay-branch-choice.png)
*Path choice at "Unterlagen vollständig?": 1 = ja, 2 = nein.*

At a parallel gateway the token splits. The join waits until both tokens have arrived.

![AND split](./media/screenshots/11-replay-parallel-split.png)
*After the AND split, "Material bestellen" and "Team einplanen" run in parallel.*

## 4. Calculating: the scenario simulation

In **Stochastic** mode bpmnsim simulates many cases at once. Each task has a duration and a cost, gateways have probabilities, and lanes become resource pools with a weekly working calendar (Monday to Friday). When a role is busy, cases queue.

![Simulation view](./media/screenshots/14-simulation-view.png)
*The simulation view: results sidebar on the right, scenario tabs at the bottom.*

### Results

![Szenario 1 results](./media/screenshots/19-szenario1-results.png)
*Szenario 1: the Verwaltung tasks are marked red as the bottleneck. The badges count task executions.*

![Szenario 2 results](./media/screenshots/21-szenario2-results.png)
*Szenario 2: the same model with more capacity and a faster check.*

The values in these screenshots:

| Metric | Szenario 1 | Szenario 2 |
| --- | --- | --- |
| Cases (completed / started) | 100 / 100 | 100 / 100 |
| Cost | €4,009.33 | €3,493.33 |
| Total cycle time (sum over all cases) | 650d 18h 00m | 86d 16h 30m |
| Average cycle time | 6d 12h 10m | 0d 20h 48m |
| Resource consumption | 2d 22h 20m | 2d 05h 20m |
| Bottleneck | Verwaltung | Verwaltung |

**Interpretation for the seminar:**

- Average cycle time drops from more than six days to under one day, because applications no longer queue in front of a single person.
- Cost also falls, mainly because the faster check needs fewer paid working hours.
- Verwaltung remains the bottleneck, but at a much lower level. The next experiment is obvious: what if only the check gets faster, or only capacity grows?

Each run draws a new random seed, so the numbers vary slightly between runs. In this run 22 applications (Szenario 1) and 20 (Szenario 2) took the "nein" path. The test behind the screenshots asserts only that Szenario 2 has a shorter average cycle time **and** lower cost than Szenario 1.

## 5. Classroom use

A 90-minute seminar session can follow exactly this sequence:

| Phase | Activity | Media |
| --- | --- | --- |
| Modelling | Students model the application process themselves | Editing video, screenshots 01–08 |
| Logic | Play every path with the replay; explain XOR and AND | Token video, screenshots 09–13 |
| Baseline | Configure and simulate Szenario 1 | Screenshots 14–19 |
| Experiment | Each group tests one change in Szenario 2 | Screenshots 20–21, calculation video |
| Presentation | Present the Excel export and argue the recommendation | Calculation video (end) |

The learning goal is to argue with evidence, not just draw a nicer diagram: **model → predict → simulate → compare → justify**.

## Limits worth knowing

- The simulator is a simplified teaching model. Inclusive, event-based and complex gateways are treated as exclusive choices, and message flows are not simulated.
- Arrivals use a fixed interval, and role calendars use simplified Monday-to-Friday working windows.
- The `.xls` export is an Excel-readable HTML table.
- Remote logging (Loki) is enabled by default and can include the full diagram XML. For courses, build with `VITE_LOKI_ENABLED=false` and use synthetic data.
